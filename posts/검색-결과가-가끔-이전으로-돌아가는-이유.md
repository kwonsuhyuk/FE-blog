검색창에 입력한 값은 최신인데 결과 목록은 가끔 이전 검색어의 데이터를 보여줬다. 다시 재현하려고 하면 잘 되고, 네트워크가 느릴 때만 드물게 나타났다.

처음에는 디바운싱 시간을 조절하면 해결될 거라고 생각했다. 하지만 문제는 요청 횟수가 아니라 **요청을 보낸 순서와 응답이 도착한 순서가 다를 수 있다는 것**이었다.

![두 검색 요청의 응답 순서가 엇갈리는 모습](/FE-blog/async-search-race-condition.png)

## 문제 상황

사용자가 검색창에 `react`를 입력한 뒤 바로 `react query`를 입력했다고 가정해보자.

```text
1. "react" 요청 시작
2. "react query" 요청 시작
3. "react query" 응답 도착 → 화면 갱신
4. "react" 응답 도착       → 화면을 이전 결과로 다시 덮어씀
```

요청은 먼저 보낸 것이 먼저 도착한다는 보장이 없다. 첫 번째 요청이 캐시를 타지 못했거나 서버에서 더 오래 걸리면 두 번째 요청보다 늦게 끝날 수 있다.

| 시점 | 입력창 | 도착한 응답 | 화면에 보이는 결과 |
| --- | --- | --- | --- |
| 1 | `react` | 없음 | 로딩 |
| 2 | `react query` | 없음 | 로딩 |
| 3 | `react query` | 두 번째 요청 | `react query` 결과 |
| 4 | `react query` | 첫 번째 요청 | `react` 결과 |

입력창과 결과가 서로 다른 상태가 된다. 에러도 발생하지 않고 API도 정상 응답했기 때문에 더 찾기 어렵다.

이런 문제를 경쟁 상태(Race Condition)라고 한다. 여러 비동기 작업이 같은 상태를 변경하려고 경쟁하고, 어떤 작업이 마지막에 끝났는지에 따라 결과가 달라지는 상황이다.

---

## 디바운싱만으로 해결되지 않는다

검색 기능을 만들 때 디바운싱을 먼저 떠올리기 쉽다.

```ts
const debouncedSearch = debounce((keyword: string) => {
  searchProducts(keyword);
}, 300);
```

디바운싱은 짧은 시간에 발생한 호출을 줄인다. `r`, `re`, `rea`, `reac`, `react` 요청을 모두 보내지 않게 해준다.

하지만 이미 시작된 두 요청의 순서는 관리하지 않는다.

```text
디바운싱이 해결하는 것 : 요청을 얼마나 자주 보낼 것인가
경쟁 상태가 묻는 것    : 어떤 응답을 화면에 반영할 것인가
```

사용자가 잠깐 멈춰 첫 요청이 시작된 다음 다시 입력하면, 디바운싱을 적용해도 두 요청은 동시에 진행될 수 있다.

→ 호출 횟수를 줄이는 것과 데이터의 최신성을 보장하는 것은 다른 문제다.

---

## 1. 이전 요청을 취소한다

`fetch`는 `AbortController`로 진행 중인 요청을 취소할 수 있다. 새 검색이 시작될 때 이전 controller를 취소하고 새 signal을 전달한다.

```tsx
import { useRef, useState } from "react";

interface IProduct {
  id: number;
  name: string;
}

export function ProductSearch() {
  const [products, setProducts] = useState<IProduct[]>([]);
  const [isLoading, setIsLoading] = useState(false);
  const controllerRef = useRef<AbortController | null>(null);

  const search = async (keyword: string) => {
    controllerRef.current?.abort();

    const controller = new AbortController();
    controllerRef.current = controller;
    setIsLoading(true);

    try {
      const response = await fetch(
        `/api/products?keyword=${encodeURIComponent(keyword)}`,
        { signal: controller.signal }
      );

      if (!response.ok) {
        throw new Error("검색 요청에 실패했다");
      }

      const data: IProduct[] = await response.json();
      setProducts(data);
    } catch (error) {
      if (error instanceof DOMException && error.name === "AbortError") {
        return;
      }

      throw error;
    } finally {
      if (controllerRef.current === controller) {
        setIsLoading(false);
      }
    }
  };

  // 입력 UI 생략
}
```

[MDN 문서](https://developer.mozilla.org/en-US/docs/Web/API/AbortController/abort)에 따르면 `abort()`는 fetch 요청뿐 아니라 응답 body 소비와 stream도 중단할 수 있다.

여기서 `finally`가 의외로 중요하다. 취소된 이전 요청이 `setIsLoading(false)`를 실행하면 새 요청이 진행 중인데도 로딩 표시가 사라질 수 있다. 데이터뿐 아니라 로딩 상태도 경쟁한다.

## 여기서 중요한 포인트

- 취소는 불필요한 네트워크와 후속 작업을 줄인다
- `AbortError`는 사용자에게 보여줄 실패가 아니므로 일반 에러와 분리한다
- 데이터, 로딩, 에러 상태는 각각 오래된 요청이 덮어쓸 수 있다

## 2. 최신 요청인지 확인한 뒤 반영한다

요청 취소만 믿기 어려운 경우도 있다. 사용하는 HTTP 클라이언트가 signal을 전달하지 않거나, 응답을 받은 뒤 별도의 비동기 가공을 수행할 수도 있다.

이럴 때는 요청마다 번호를 붙이고 가장 최근 요청만 상태를 바꾸게 할 수 있다.

```tsx
const latestRequestIdRef = useRef(0);

const search = async (keyword: string) => {
  const requestId = ++latestRequestIdRef.current;
  setIsLoading(true);

  try {
    const response = await fetch(
      `/api/products?keyword=${encodeURIComponent(keyword)}`
    );
    const data: IProduct[] = await response.json();

    if (requestId !== latestRequestIdRef.current) {
      return;
    }

    setProducts(data);
  } catch (error) {
    if (requestId !== latestRequestIdRef.current) {
      return;
    }

    setError(error instanceof Error ? error.message : "알 수 없는 오류");
  } finally {
    if (requestId === latestRequestIdRef.current) {
      setIsLoading(false);
    }
  }
};
```

이 방식은 이전 요청 자체를 멈추지는 않는다. 대신 오래된 응답이 도착해도 UI 상태에는 반영하지 않는다.

| 방법 | 네트워크 요청 중단 | 오래된 상태 반영 방지 |
| --- | --- | --- |
| AbortController | 가능 | 취소가 정상 전달되면 가능 |
| requestId 비교 | 불가능 | 가능 |
| 두 방법 함께 사용 | 가능 | 가능 |

둘 중 하나만 정답은 아니다. 검색처럼 이전 결과가 더 이상 필요 없는 화면이라면 취소와 최신성 검사를 같이 두는 편이 안전하다.

> 요청을 취소하는 것은 자원 관리이고, 최신 응답만 반영하는 것은 상태 일관성 관리다.

## 3. TanStack Query를 쓴다면 queryKey부터 본다

라이브러리를 쓴다고 경쟁 상태가 자동으로 사라지는 것은 아니다. 검색어가 queryKey에 포함되어야 서로 다른 검색 결과가 다른 캐시로 관리된다.

```tsx
const productsQuery = useQuery({
  queryKey: ["products", keyword],
  queryFn: async ({ signal }) => {
    const response = await fetch(
      `/api/products?keyword=${encodeURIComponent(keyword)}`,
      { signal }
    );

    if (!response.ok) {
      throw new Error("검색 요청에 실패했다");
    }

    return response.json() as Promise<IProduct[]>;
  },
  enabled: keyword.trim().length > 0,
});
```

TanStack Query의 [query cancellation 문서](https://tanstack.com/query/latest/docs/framework/query-cancellation)는 query function에 `AbortSignal`을 전달한다. 다만 `fetch`에 signal을 넘겨야 실제 네트워크 요청도 취소된다.

다음처럼 검색어를 key에서 빼면 모든 검색 결과가 같은 데이터로 취급된다.

```tsx
// X : 검색어가 달라도 같은 캐시
queryKey: ["products"]

// O : 검색어별로 캐시를 구분
queryKey: ["products", keyword]
```

`queryKey`는 단순한 이름이 아니다. 어떤 입력이 달라졌을 때 다른 데이터로 봐야 하는지를 표현하는 의존성에 가깝다.

## 로딩 상태도 하나의 boolean이면 부족할 수 있다

요청이 하나뿐이라고 생각하면 `isLoading: boolean`이면 충분해 보인다. 하지만 동시에 여러 요청이 존재할 수 있다면 boolean은 어떤 요청의 상태인지 설명하지 못한다.

```ts
type SearchState =
  | { status: "idle" }
  | { status: "loading"; requestId: number; keyword: string }
  | { status: "success"; requestId: number; keyword: string; data: IProduct[] }
  | { status: "error"; requestId: number; keyword: string; message: string };
```

상태에 `requestId`와 `keyword`를 같이 넣으면 현재 화면이 어떤 요청의 결과인지 추적하기 쉬워진다. 모든 프로젝트에 이런 union type이 필요한 것은 아니다. 다만 버그를 잡을 때 상태를 boolean 여러 개로 쪼개는 것보다 전이 가능한 상태를 명시하는 편이 도움이 된다.

```text
idle → loading(3, "react query") → success(3, "react query")
```

여기에 `success(2, "react")`가 끼어들려고 하면 오래된 응답이라는 사실이 눈에 보인다.

## 재현하기 어려운 버그를 일부러 만든다

로컬에서는 API가 빨라서 경쟁 상태가 잘 나타나지 않는다. 그래서 응답 시간을 의도적으로 다르게 만들었다.

```ts
const delay = (ms: number) =>
  new Promise((resolve) => setTimeout(resolve, ms));

async function mockSearch(keyword: string) {
  const delayMs = keyword === "react" ? 1500 : 200;
  await delay(delayMs);

  return [{ id: 1, name: `${keyword} result` }];
}
```

이 상태에서 `react` 요청을 보내고 바로 `react query`를 요청하면 항상 이전 응답이 나중에 도착한다. 운이 나빠야 발생하던 버그를 매번 발생하는 테스트 조건으로 바꾼 셈이다.

브라우저 개발자 도구에서도 Network throttling을 켜고 확인할 수 있다. 다만 전체 네트워크가 같이 느려지므로 특정 요청의 순서를 보장해서 재현하려면 mock delay가 더 편했다.

## 여기서 중요한 포인트

- 비동기 버그는 기다려서 발견하는 게 아니라 순서를 조작해서 재현한다
- 성공 데이터만 보지 말고 로딩과 에러가 최신 요청에 속하는지도 확인한다
- 빠르게 입력하기, 검색어 지우기, 페이지 이동하기도 같이 테스트한다

---

## 자주 하는 실수

### 1) 디바운싱 시간을 계속 늘린다

요청 수는 줄지만 이미 시작된 요청의 응답 순서는 그대로다. 사용자는 결과를 더 늦게 볼 뿐이다.

### 2) AbortError도 일반 오류로 보여준다

새 검색 때문에 정상적으로 취소된 요청인데 "검색에 실패했습니다" 토스트가 뜬다. 취소와 실패는 다른 상태다.

### 3) 데이터만 보호하고 로딩 상태는 그대로 둔다

오래된 응답이 목록은 바꾸지 못해도 로딩이나 에러를 바꾸면 화면이 다시 어긋난다.

### 4) queryKey를 고정한다

필터, 정렬, 페이지, 검색어가 달라지는데 같은 key를 사용하면 서로 다른 데이터를 같은 캐시로 취급하게 된다.

---

## 정리

- 요청을 보낸 순서와 응답이 도착하는 순서는 다를 수 있다
- 디바운싱은 호출 횟수를 줄일 뿐 최신성을 보장하지 않는다
- `AbortController`로 이전 요청을 취소할 수 있다
- requestId를 비교하면 오래된 응답의 상태 변경을 막을 수 있다
- TanStack Query에서는 검색 조건을 queryKey에 포함하고 signal을 실제 요청에 전달한다
- 비동기 버그는 응답 지연을 조작해 재현 가능한 상태로 만든다

---

## 마무리 하며

처음에는 검색 API가 정상적으로 응답하니 프론트엔드에서 더 볼 게 없다고 생각했다. 하지만 각각의 요청이 정상인 것과 화면이 항상 최신 상태인 것은 다른 문제였다.

비동기 코드를 볼 때 이제는 "요청이 성공하는가"만 보지 않고 "이 응답이 아직도 화면에 반영할 자격이 있는가"를 같이 보려고 한다. 포트폴리오에서 검색 기능 하나를 만들더라도 이런 경계 조건까지 설명할 수 있다면 단순히 API를 연결한 것과는 차이가 있다고 생각한다.
