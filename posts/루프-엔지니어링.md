요즘 개발자 타임라인에 가장 자주 보이는 단어 중 하나인 루프 엔지니어링에 대해서 개념과, 프론트엔드 프로젝트에 실제로 붙이는 방법을 간단하게 기록하려고 한다.

## 루프 엔지니어링이란 ?

루프 엔지니어링(Loop Engineering)은 AI 에이전트에게 **매번 프롬프트를 입력하던 사람의 자리를, 그 일을 대신하는 시스템으로 대체하는 설계 작업**이다.

지금까지 에이전트를 쓰던 방식은 대략 이랬다.

1. 지시를 입력한다
2. 결과를 본다
3. 잘못된 부분을 지적한다
4. 다시 지시한다

여기서 문제는 **사람이 곧 루프**라는 점이다.

- 에이전트는 초 단위로 코드를 만드는데, 확인하고 다시 지시하는 건 분 단위다
- 전체 처리량이 사람의 반응 속도에 묶인다
- 사람의 검토 품질은 일정하지 않다 (새벽에 하는 "대충 괜찮네"가 그대로 통과한다)

루프 엔지니어링은 이 자리를 시스템으로 바꾼다. 사람은 목표와 경계 조건만 정하고, 발견 → 계획 → 실행 → 검증 → 반복은 시스템이 돌린다.

2026년 6월 초에 이 용어가 퍼졌다.

- Peter Steinberger : 코딩 에이전트에 프롬프트를 치지 말고, 에이전트에게 프롬프트를 주는 루프를 설계하라
- Boris Cherny (Claude Code) : 더 이상 직접 프롬프트를 치지 않고 루프를 짜며, 그 루프가 일을 한다
- Addy Osmani : 위 흐름에 「Loop Engineering」이라는 이름과 구조를 붙임

용어의 계보는 이렇게 이어진다.

```
프롬프트 엔지니어링  →  컨텍스트 엔지니어링  →  루프 엔지니어링
 (메시지 한 개)         (모델이 보는 것 전체)     (메시지를 둘러싼 사이클 전체)
```

여기서 중요한 건 **대체가 아니라 감싸는 관계**라는 것이다. 루프 안에서도 좋은 프롬프트는 여전히 필요하다. 다만 매일 손대야 하는 대상에서는 빠진다.

## 루프의 기본 구조

루프의 안쪽은 사실 아주 단순한 반복문이다.

```js
while (!done) {
  const plan = decideNextStep(goal, state); // 다음 한 걸음 결정
  const result = act(plan);                 // 실행
  state = observe(result, state);           // 결과 관찰 + 기록
  done = verify(state);                     // 완료 판정
}
```

이 while 문 자체는 이미 대부분의 에이전트 도구가 구현해두었다. 실제로 설계해야 하는 건 이 **루프의 바깥**이다.

### 1) 목표 (goal)

무엇을 완료로 볼 것인지. 검증 가능한 문장이어야 한다.

### 2) 가이드 파일

프로젝트 컨벤션과 하지 말아야 할 것. 매 실행마다 읽힌다.

### 3) 검증 (verify)

기계가 판정할 수 있는 완료 신호. 루프의 핵심이다.

### 4) 상태 (memory)

에이전트는 세션이 끝나면 잊는다. 저장소는 잊지 않는다.

### 5) 종료 조건

성공했을 때와 포기할 때. 둘 다 없으면 루프가 아니라 사고다.

## 1단계 : 검증부터 만든다

백엔드는 루프 붙이기가 쉽다. 테스트 통과 여부가 명확하기 때문이다.
반면 프론트엔드는 "잘 나오는가"가 애매해서 완료 판정이 어렵다.

그래서 루프를 짜기 전에 할 일은 프롬프트를 다듬는 게 아니라 **기계가 읽을 수 있는 완료 신호를 만드는 것**이다.
이게 없으면 코드를 쓴 에이전트가 자기 결과를 자기가 채점하는데, 자기 채점은 항상 후하다.

프론트엔드에서 쓸 수 있는 검증 신호는 다음과 같다.

| 신호      | 도구                    | 잡아내는 것             |
| --------- | ----------------------- | ----------------------- |
| 타입 검사 | `tsc --noEmit`          | props 불일치, 시그니처 |
| 린트      | ESLint                  | 컨벤션, hooks 규칙     |
| 유닛      | Vitest                  | 컴포넌트 동작           |
| E2E       | Playwright              | 실제 렌더링, 라우팅    |
| 접근성    | axe-core                | a11y 회귀               |
| 번들 크기 | size-limit              | 무심코 늘어난 JS       |
| 빌드      | `next build`            | 배포 가능 여부          |

전부 갖출 필요는 없다. 다만 **단일 진입점**은 반드시 필요하다.
에이전트에게 "이게 통과할 때까지"라고 말할 수 있는 명령 하나가 있어야 한다.

```bash
#!/usr/bin/env bash
# scripts/verify.sh
set -euo pipefail

fail=0

step() {
  echo "▶ $1"
  shift
  # 하나가 실패해도 바로 멈추지 않고 전부 돌린 뒤 결과를 모은다
  # 이유: 에이전트가 한 번에 여러 문제를 보고 고칠 수 있게 하기 위해서다
  if ! "$@"; then
    fail=1
  fi
}

step "typecheck" npx tsc --noEmit
step "lint"      npx eslint . --max-warnings=0
step "unit"      npx vitest run
step "build"     npm run build
step "e2e"       npx playwright test

if [ "$fail" -ne 0 ]; then
  echo "❌ 검증 실패"
  exit 1
fi

echo "✅ 검증 통과"
```

## **여기서 중요한 포인트**

- `--max-warnings=0` : 경고를 허용하면 에이전트는 "경고는 통과"로 해석한다. 게이트는 이분법이어야 한다
- 종료 코드로 판정한다. 에이전트의 "다 됐습니다"가 아니라 exit code가 판정 기준이다
- 이 스크립트 하나만 만들어도 절반은 온 것이다

접근성은 Playwright에 얹어두면 루프가 알아서 봐준다.

```ts
// e2e/a11y.spec.ts
import { test, expect } from "@playwright/test";
import AxeBuilder from "@axe-core/playwright";

const routes = ["/", "/posts", "/about"];

for (const route of routes) {
  test(`a11y: ${route}`, async ({ page }) => {
    await page.goto(route);

    const { violations } = await new AxeBuilder({ page })
      .withTags(["wcag2a", "wcag2aa"])
      .analyze();

    // 위반 목록이 비어있어야 통과 -> 종료 조건이 숫자로 딱 떨어진다
    expect(violations.map((v) => v.id)).toEqual([]);
  });
}
```

## 2단계 : 가이드 파일

에이전트는 세션마다 콜드 스타트한다. 컨벤션을 매번 다시 설명하면 그게 그대로 토큰이자 실수 비용이 된다.
그래서 규칙과 **의도**를 파일로 한 번 정리해두고 루프가 매 실행마다 읽게 한다.

```markdown
<!-- CLAUDE.md -->
# 프로젝트 규칙

## 스택
- Next.js App Router (Pages Router 코드 추가 금지)
- Tailwind CSS v4 : tailwind.config.js가 아니라 app/globals.css의 @theme에서 토큰 관리
- Framer Motion은 클라이언트 컴포넌트에서만 사용

## 컨벤션
- 서버 컴포넌트가 기본. "use client"는 상태/이벤트/모션이 필요한 최말단에만 붙인다
- 색상은 임의값(text-[#333]) 대신 @theme에 정의된 토큰만 사용한다
- 포스트는 posts/*.md에서 읽는다. frontmatter는 title, date, category 세 개

## 하지 않는 것 (사건 기록)
- next/image의 unoptimized를 끄지 말 것 -> GitHub Pages 정적 배포라 최적화 서버가 없다
- trailing slash 설정을 건드리지 말 것 -> Pages 배포 경로가 깨진 적 있음
- 테스트를 삭제하거나 .skip으로 우회하지 말 것 -> 실패하면 원인을 고친다

## 검증
- 완료 판정은 ./scripts/verify.sh 하나로 한다
```

## **여기서 중요한 포인트**

- "하지 않는 것" 섹션이 제일 값어치를 한다. 같은 실수를 반복할 때마다 한 줄씩 늘리면 된다
- 규칙만 쓰지 말고 **왜 그런지**를 같이 쓴다. 이유가 없으면 에이전트가 나름의 판단으로 규칙을 우회한다

## 3단계 : 루프 스크립트

이제 실제 루프다. Claude Code의 헤드리스 모드(`-p`)를 쓴 예시다.

```bash
#!/usr/bin/env bash
# scripts/loop.sh
set -uo pipefail

MAX_ITER=${MAX_ITER:-6}          # 종료 조건 1 : 최대 반복 횟수
GOAL_FILE=${GOAL_FILE:-GOAL.md}  # 목표
STATE_FILE=${STATE_FILE:-PROGRESS.md}  # 회차 간 기억

for ((i = 1; i <= MAX_ITER; i++)); do
  echo "──────── iteration $i / $MAX_ITER ────────"

  # 매 회차마다 [목표 + 지금까지의 진행 상황]을 다시 넣어준다
  # 에이전트는 이전 세션을 기억하지 못하므로 상태 파일이 곧 기억이 된다
  claude -p "너는 이 저장소의 구현 담당이다. CLAUDE.md의 규칙을 따른다.

## 목표
$(cat "$GOAL_FILE")

## 지금까지의 진행 상황
$(cat "$STATE_FILE")

## 이번 턴에 할 일
목표에 가까워지는 '다음 한 걸음'만 수행해라. 전부 끝내려 하지 마라.
끝나면 PROGRESS.md에 [무엇을 했는지 / 무엇이 남았는지]를 덧붙여라.
테스트를 삭제하거나 skip 처리해서 통과시키는 것은 실패로 간주한다." \
    --allowedTools "Read,Edit,Write,Bash(npm run *),Bash(npx *),Bash(git *)" \
    --max-turns 30

  # 종료 조건 2 : 검증 통과
  if ./scripts/verify.sh; then
    echo "✅ 검증 통과 - $i 회차에서 종료"
    git add -A && git commit -m "loop: 목표 달성 ($i 회차)"
    exit 0
  fi

  # 실패해도 체크포인트를 남긴다 -> 3회차에서 망가지면 2회차로 되돌리면 된다
  echo "⚠️ 검증 실패 - 체크포인트 남기고 다음 회차로"
  git add -A && git commit -m "loop: checkpoint $i" || true
done

echo "🛑 최대 반복 횟수 도달. 사람이 확인해야 함"
exit 1
```

## **여기서 중요한 포인트**

- 종료 조건이 **두 개**다 : 성공(verify 통과)과 포기(MAX_ITER 도달)
- 한 턴에 **한 걸음**만 시킨다. "전부 끝내라"고 하면 컨텍스트가 터지고 되돌리기도 어렵다
- 권한을 좁힌다. `Bash`를 통째로 열지 않고 `Bash(npm run *)`처럼 패턴으로 범위를 지정한다
- 회차마다 커밋을 남긴다. 체크포인트 없는 자율 루프는 롤백이 불가능하다

목표 파일은 이렇게 쓴다.

```markdown
<!-- GOAL.md -->
포스트 목록 페이지에 카테고리 필터를 추가한다.

완료 조건:
- /posts 에서 카테고리 버튼으로 목록이 필터링된다
- 선택한 카테고리가 URL 쿼리(?category=Dev)에 반영되고 새로고침해도 유지된다
- e2e/posts-filter.spec.ts 에 필터 동작 테스트가 있고 통과한다
- 기존 a11y 테스트가 계속 통과한다
- 번들 예산(180KB)을 넘지 않는다
```

"카테고리 필터 예쁘게 만들어줘"가 아니라 위처럼 쓰는 순간 루프가 돌 수 있는 문제로 바뀐다.

## 4단계 : 작성자와 검증자를 나눈다

코드를 쓴 에이전트가 자기 결과를 채점하면 신뢰가 생기지 않는다.
그래서 만드는 쪽과 검증하는 쪽을 나눈다.

```bash
# verify.sh 통과 후, 기계가 못 잡는 부분을 별도 에이전트에게 검토시킨다
review=$(claude -p "직전 커밋의 diff를 검토해라.
CLAUDE.md 규칙 위반, 테스트 우회(삭제/skip/조건 완화),
불필요한 의존성 추가, 'use client' 남용을 찾아라.
파일을 수정하지 마라.
문제가 없으면 정확히 PASS 한 단어만 출력하고, 있으면 목록으로 출력해라." \
  --allowedTools "Read,Bash(git diff *),Bash(git show *)" \
  --max-turns 10)

if [ "$review" != "PASS" ]; then
  # 반려 사유를 상태 파일에 적어 다음 회차 입력으로 넘긴다
  printf '\n## 리뷰 반려 (%s회차)\n%s\n' "$i" "$review" >> "$STATE_FILE"
  continue
fi
```

검증자에게는 **쓰기 권한을 주지 않는 것**이 포인트다.
읽고 판정만 하게 하면 "지적하고 자기가 고쳐서 통과시키는" 자기 봐주기가 구조적으로 불가능해진다.

## 5단계 : CI로 옮긴다

로컬에서 손으로 돌리는 루프는 결국 안 돌리게 된다. 트리거를 CI에 두면 그때부터 시스템이 된다.

```yaml
# .github/workflows/nightly-loop.yml
name: Nightly Maintenance Loop

on:
  schedule:
    - cron: "0 18 * * 1-5" # UTC 18:00 = KST 새벽 3시, 평일
  workflow_dispatch:

permissions:
  contents: write
  pull-requests: write

jobs:
  loop:
    runs-on: ubuntu-latest
    timeout-minutes: 45 # 종료 조건 3 : 시간
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: npx playwright install --with-deps chromium

      - name: Run loop
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          MAX_ITER: 4
        run: ./scripts/loop.sh

      # 루프의 출력은 main 직접 푸시가 아니라 PR 이어야 한다
      - name: Open PR
        if: success()
        uses: peter-evans/create-pull-request@v6
        with:
          branch: loop/${{ github.run_id }}
          title: "chore: nightly loop 결과"
          body: "자동 루프가 만든 변경. PROGRESS.md를 먼저 볼 것"
```

## **여기서 중요한 포인트**

- **출력은 PR로.** main에 직접 푸시하면 아침에 블로그가 깨져 있는 상황이 생긴다. PR은 사람이 개입할 지점을 강제로 만든다
- **타임아웃과 예산을 반드시 건다.** 잘못 설계된 루프의 대표 실패 모드는 틀린 답이 아니라 **밤새 조용히 토큰을 태우는 것**이다
- 이슈나 PR 코멘트를 트리거로 쓰고 싶다면 공식 액션(`anthropics/claude-code-action@v1`)이 배선이 더 간단하다

## 루프가 잘 도는 케이스

아무 작업이나 루프로 만들면 안 된다.
**완료 판정이 기계적으로 가능하고, 실패해도 되돌리기 쉬운 것**이 좋은 후보다.

### 1. 의존성 스윕

`npm outdated`로 목록을 뽑고 패키지 하나씩 올리면서 verify를 돌린다.
통과하면 커밋, 실패하면 되돌리고 "수동 확인 필요"로 기록한다.
완료 조건이 명확해서 가장 안정적으로 도는 종류다.

### 2. a11y 스윕

axe 위반을 라우트별로 수집해 하나씩 고친다.
위반 개수 0이 종료 조건이라 딱 떨어진다.

### 3. 번들 워치독

size-limit을 초과하면 원인 청크를 찾아 `next/dynamic`으로 쪼개는 PR을 연다.
성공 여부가 숫자로 판정된다.

### 4. 테스트 백필

커버리지가 낮은 컴포넌트부터 테스트를 채운다.
다만 보상 해킹이 가장 잘 일어나는 영역이라 검증자 에이전트를 반드시 붙여야 한다.
(`expect(true).toBe(true)`로 커버리지 숫자만 올리는 경우를 몇 번 봤다)

---

## 루프에 넣으면 안 되는 것

- "디자인을 더 세련되게"
- "카피를 더 매력적으로"
- "UX를 개선해줘"

→ 종료 조건을 쓸 수 없다. 루프가 영원히 만족하지 못하거나, 반대로 첫 시도에 스스로 만족해버린다.
이런 건 그냥 대화형으로 하는 게 낫다.

---

## 자주 하는 실수

### 1) 종료 조건을 안 정함

```bash
MAX_ITER=${MAX_ITER:-6}
timeout-minutes: 45
```

언제 멈출지, 잘못되면 어떻게 빠져나올지를 **먼저** 설계해야 한다. 모델 성능이 좋다고 루프가 알아서 안전하게 끝나지 않는다.

### 2) 보상 해킹 (테스트를 지워서 통과시킴)

```bash
--allowedTools "Read,Bash(git diff *)"   # 검증자에게는 쓰기 권한 없음
```

만드는 에이전트와 검증하는 에이전트를 나누는 것이 신뢰의 출발점이다.

### 3) 체크포인트 없음

```bash
git add -A && git commit -m "loop: checkpoint $i" || true
```

회차마다 커밋을 안 남기면 어디서 망가졌는지 알 수 없고 되돌릴 수도 없다.

### 4) 권한을 통째로 열어줌

```bash
# X : Bash 전체 허용
# O : Bash(npm run *),Bash(npx *)
```

프론트엔드 루프에 `rm`이나 배포 명령이 필요한 경우는 거의 없다.

### 5) 이해 부채

가장 조용하고 가장 위험한 실수다.
루프가 잘 돌수록 저장소에는 내가 읽지 않은 코드가 쌓인다.
**통과한 테스트는 코드가 동작한다는 증거이지, 내가 그 코드를 이해했다는 증거는 아니다.**

## 정리

| 구분      | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 | 루프 엔지니어링          |
| --------- | ------------------- | ------------------- | ------------------------ |
| 최적화 대상 | 메시지 한 개       | 모델이 보는 것 전체 | 사이클 전체              |
| 사람의 역할 | 조작자             | 조작자              | 설계자                   |
| 개입 시점 | 매 턴               | 매 턴               | 종료 시 / 중요 결정 시   |
| 핵심 난이도 | 표현               | 맥락 구성           | 검증과 종료 조건         |
| 실패 모드 | 답이 애매함         | 맥락 부족           | 무한 루프 / 비용 / 보상 해킹 |

### 도입 순서

- **1주차** : `verify.sh` 하나 만들고, 지시 끝에 "이게 통과할 때까지" 붙이기
- **2주차** : `CLAUDE.md` 만들고 틀릴 때마다 규칙 한 줄씩 추가
- **3~4주차** : `loop.sh` 스크립트화 (종료 조건, 최대 반복, 회차별 커밋)
- **2개월차** : 검증자 분리, GitHub Actions로 트리거 이동, PR 출력
- **계속** : 루프 1회당 비용, 사람 개입률, 반려율 측정

### 실전에서 빠르게 판단하는 방법

- 완료 조건을 스크립트로 쓸 수 있으면 → 루프
- "더 좋게" 같은 말이 들어가면 → 대화형
- 실패해도 되돌리기 쉬우면 → 루프
- 되돌리기 어려우면 → 사람이 직접

## 마무리 하며

루프 엔지니어링에서 새로운 기술은 사실 거의 없다.
반복문, 셸 스크립트, 테스트, cron, CI. 전부 원래 있던 것들이다.
바뀐 건 조립하는 목적이다. 예전에는 사람이 **실행할 것**을 자동화했다면, 이제는 사람이 **판단할 것**을 자동화한다.

그래서 결론은 하나다.
좋은 루프를 만드는 건 좋은 프롬프트를 쓰는 능력이 아니라, **무엇을 완료로 볼 것인지 정의하는 능력**이다.
프론트엔드는 그게 특히 어렵고, 그래서 더 해볼 만하다.

물론 회의론도 정당하다. 쿠버네티스도 제어 루프 위에 서 있지만 그건 결정론적 루프라는 지적이 있고, 지금은 열광이 엔지니어링을 앞질렀다는 이야기도 나온다.
다만 `verify.sh`와 `CLAUDE.md`를 만드는 일은 루프를 안 돌리더라도 어차피 해두면 좋은 일이라, 여기서부터 시작하면 손해볼 게 없다고 생각한다.

새로 나온 개념이라 정의가 아직 조금씩 다르지만, 프론트엔드 프로젝트에 붙이는 관점에서 간단하게 정리해봤다!
