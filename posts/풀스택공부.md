# 프론트와 백엔드를 따로 공부했는데, 풀스택은 결국 연결을 이해하는 일이었다

풀스택 개발을 공부하기 전에는 프론트엔드와 백엔드를 별개의 영역으로 생각했다.

프론트엔드는 화면을 만들고,

백엔드는 데이터를 저장하는 정도로 이해했다.

하지만 직접 하나의 기능을 처음부터 끝까지 연결해 보니 풀스택 개발에서 중요한 것은 여러 기술을 많이 아는 것이 아니었다.

사용자의 행동이 어떤 요청으로 바뀌고, 서버와 데이터베이스를 거쳐 다시 화면에 반영되는지 **전체 흐름을 이해하는 것**이 더 중요했다.

이번 공부에서는 화면 하나를 완성하는 데 집중하기보다 프론트엔드, API, 서버, 데이터베이스가 어떤 책임을 나누는지 이해하려고 했다.

---

# 처음에는 화면과 서버를 따로 공부했다

처음에는 프론트엔드와 백엔드를 각각 공부했다.

프론트엔드에서는

- 컴포넌트
- 상태 관리
- 이벤트 처리
- API 호출

을 중심으로 봤다.

백엔드에서는

- 라우팅
- 요청과 응답
- 데이터 검증
- 데이터베이스 연동

을 공부했다.

각각의 개념만 볼 때는 크게 어렵지 않았다.

버튼을 누르면 상태가 바뀌고,

API 요청이 들어오면 서버가 JSON을 반환했다.

하지만 두 영역을 연결하는 순간부터 생각해야 할 것이 많아졌다.

프론트엔드에서 보낸 데이터의 형태와 서버가 기대하는 형태가 달랐고, 서버에서 오류가 발생했을 때 화면에서는 단순히 "동작하지 않는다"는 결과만 보이기도 했다.

그때부터 기능 하나를 프론트엔드와 백엔드로 나눠 보기보다 **하나의 요청 흐름으로 보기 시작했다.**

---

# 게시글 작성 기능으로 전체 흐름을 따라갔다

전체 구조를 이해하기 위해 게시글 작성처럼 단순한 기능을 기준으로 흐름을 따라갔다.

사용자가 제목과 내용을 입력하고 등록 버튼을 누르면 다음 과정이 진행된다.

```
사용자 입력

↓

프론트엔드 상태 변경

↓

POST 요청

↓

서버에서 데이터 검증

↓

데이터베이스 저장

↓

응답 반환

↓

화면 갱신
```

코드로 보면 짧은 기능이지만 실제로는 여러 계층이 연결되어 있었다.

프론트엔드는 입력값을 관리하고 요청을 보내는 역할을 했다.

서버는 요청한 사용자가 올바른지 확인하고, 전달받은 값이 유효한지 검증했다.

데이터베이스는 검증이 끝난 데이터를 저장하고, 서버는 처리 결과에 맞는 상태 코드와 응답을 반환했다.

이 과정을 직접 연결하면서 풀스택 개발은 모든 영역의 코드를 혼자 작성하는 일이 아니라 **각 영역의 책임과 경계를 이해하는 일**에 가깝다고 느꼈다.

---

# API를 단순한 주소로만 보면 안 됐다

처음에는 API를 프론트엔드가 데이터를 가져오기 위해 호출하는 주소 정도로 생각했다.

예를 들어

```
GET /api/posts
```

는 게시글 목록을 가져오고,

```
POST /api/posts
```

는 게시글을 등록하는 식이었다.

하지만 실제로 연결해 보니 URL보다 중요한 것은 **프론트엔드와 백엔드가 어떤 형태의 데이터를 주고받기로 약속했는지**였다.

요청 필드의 이름이 다르거나, 성공 응답과 실패 응답의 구조가 일정하지 않으면 프론트엔드에서 예외 처리가 복잡해졌다.

그래서 API를 만들 때는 다음 내용을 함께 정해야 했다.

- 어떤 HTTP Method를 사용할지
- 요청 데이터는 어떤 형태인지
- 성공했을 때 무엇을 반환할지
- 실패했을 때 어떤 상태 코드를 사용할지
- 오류 메시지는 어떤 구조로 내려줄지

예를 들어 제목이 비어 있을 때 단순히 문자열만 반환하는 것보다

```json
{
  "code": "INVALID_TITLE",
  "message": "제목을 입력해 주세요."
}
```

처럼 오류 코드를 함께 전달하면 프론트엔드에서도 상황에 맞는 처리를 하기 쉬웠다.

API는 서버에 있는 기능을 호출하는 수단이 아니라, **프론트엔드와 백엔드 사이의 계약**에 가까웠다.

---

# 프론트엔드에서는 성공한 화면만 만들면 안 됐다

처음에는 API에서 받은 데이터를 화면에 출력하는 것에만 집중했다.

하지만 실제 서비스의 화면은 데이터가 정상적으로 도착한 순간만 존재하지 않는다.

요청을 보내고 있는 상태가 있고,

데이터가 하나도 없는 상태가 있으며,

요청이 실패한 상태도 있다.

그래서 하나의 목록 화면에도 최소한 다음 상태가 필요했다.

- Loading
- Success
- Empty
- Error

이 상태들을 구분하지 않으면 서버 응답이 늦을 때 빈 화면이 보이거나, 오류가 발생했는데도 사용자에게 아무런 안내를 하지 못했다.

또한 화면에서 사용하는 상태를 모두 같은 방식으로 관리할 필요는 없었다.

모달이 열려 있는지, 어떤 탭을 선택했는지 같은 값은 프론트엔드 내부의 상태였다.

반면 게시글 목록이나 사용자 정보는 서버가 원본을 가지고 있는 상태였다.

두 종류의 상태를 구분한 뒤부터 어디에서 값을 변경하고 언제 다시 조회해야 하는지가 조금 더 명확해졌다.

---

# 데이터 검증은 프론트에서 끝나지 않았다

입력 폼을 만들면서 프론트엔드에서 제목의 길이나 필수 입력 여부를 검사했다.

사용자가 잘못된 값을 입력했을 때 바로 알려줄 수 있어서 필요한 작업이었다.

하지만 프론트엔드의 검증만으로는 충분하지 않았다.

브라우저에서 보내는 요청은 개발자 도구나 별도의 프로그램을 통해 얼마든지 변경할 수 있기 때문이다.

결국 서버에서도 같은 값을 다시 검증해야 했다.

프론트엔드 검증은 사용자 경험을 위한 것이고,

백엔드 검증은 데이터의 신뢰성을 지키기 위한 것이었다.

이 차이를 이해한 뒤에는 화면에서 이미 확인한 값이라도 서버에서 그대로 신뢰하지 않게 됐다.

---

# 인증과 인가도 다른 문제였다

로그인 기능을 공부할 때 가장 헷갈렸던 부분은 인증과 인가였다.

처음에는 로그인한 사용자만 확인하면 된다고 생각했다.

하지만 로그인에 성공했다는 사실이 모든 작업을 할 수 있다는 의미는 아니었다.

인증은

> 이 요청을 보낸 사용자가 누구인가

를 확인하는 과정이고,

인가는

> 이 사용자가 이 작업을 수행할 권한이 있는가

를 확인하는 과정이었다.

예를 들어 로그인한 사용자가 게시글 수정 API를 호출하더라도, 해당 게시글의 작성자가 아니라면 서버에서 요청을 거절해야 한다.

화면에서 수정 버튼을 숨기는 것만으로는 충분하지 않았다.

API를 직접 호출할 수도 있기 때문에 최종 권한 확인은 서버에서 이루어져야 했다.

인증 기능을 공부하면서 보안은 별도의 기능이 아니라 모든 요청 흐름에 포함되어야 하는 조건이라는 것을 알게 됐다.

---

# 오류가 발생하면 계층별로 확인했다

풀스택 공부에서 가장 어려웠던 부분은 오류가 발생한 위치를 찾는 일이었다.

화면에 게시글이 보이지 않아도 원인은 여러 곳에 있을 수 있었다.

- 버튼 이벤트가 실행되지 않았는지
- 요청 주소가 잘못됐는지
- 서버에서 오류가 발생했는지
- 데이터베이스에 값이 저장되지 않았는지
- 응답 데이터와 프론트엔드 타입이 다른지

처음에는 관련 코드를 한꺼번에 수정하면서 원인을 찾으려고 했다.

그러다 보니 우연히 동작하더라도 무엇이 문제였는지 정확히 알기 어려웠다.

이후에는 브라우저의 Network 탭에서 요청이 실제로 전송됐는지 먼저 확인했다.

요청이 정상이라면 서버 로그를 보고,

그다음 데이터베이스에 값이 저장됐는지 확인했다.

프론트엔드

↓

네트워크

↓

백엔드

↓

데이터베이스

순서로 범위를 좁히니 문제를 찾는 과정이 훨씬 명확해졌다.

---

# 로컬에서 동작하는 것이 끝은 아니었다

처음에는 개발 서버에서 기능이 정상적으로 동작하면 구현이 끝났다고 생각했다.

하지만 배포를 생각하면 추가로 확인해야 할 내용이 많았다.

- 개발 환경과 운영 환경의 설정 분리
- 환경 변수를 이용한 비밀 정보 관리
- 데이터베이스 마이그레이션
- CORS 설정
- HTTPS 적용
- 오류 로그와 모니터링

특히 데이터베이스 주소나 인증 키를 코드에 직접 작성하면 안 된다는 것은 알고 있었지만, 실제로 프론트엔드에 포함해도 되는 환경 변수와 서버에서만 관리해야 하는 값을 구분하는 과정이 필요했다.

기능이 동작하는 코드와 운영할 수 있는 서비스 사이에는 생각보다 큰 차이가 있었다.

---

# 풀스택 공부를 하며 가장 크게 바뀐 점

풀스택을 공부하면서 가장 크게 바뀐 것은 문제를 보는 범위였다.

예전에는 화면에서 오류가 발생하면 프론트엔드 코드만 확인했다.

지금은

- 요청이 올바르게 만들어졌는지
- 서버가 어떤 응답을 반환했는지
- 데이터베이스의 값이 기대한 상태인지
- 각 계층의 책임이 섞이지 않았는지

를 함께 보려고 한다.

프론트엔드와 백엔드를 모두 안다는 것은 모든 기술에 능숙하다는 의미가 아니었다.

문제가 발생했을 때 전체 흐름 안에서 원인의 위치를 찾고, 각 영역이 어떤 책임을 가져야 하는지 판단할 수 있다는 의미에 더 가까웠다.

---

# 마무리

풀스택 개발을 공부하면서 여러 기술을 한 번에 익히는 것보다 작은 기능을 끝까지 연결해 보는 것이 더 도움이 됐다.

게시글을 등록하는 단순한 기능도 사용자 입력, 상태 관리, API, 데이터 검증, 인증, 데이터베이스가 모두 연결되어 있었다.

각 기술을 따로 공부할 때는 보이지 않던 부분이었다.

아직 프론트엔드와 백엔드 모두 더 공부해야 할 내용이 많다.

하지만 이제는 새로운 기술을 추가하는 것보다

> 이 데이터는 어디에서 시작해서 어디까지 이동하는가

를 먼저 생각하게 됐다.

결국 풀스택 개발은 프론트엔드와 백엔드를 모두 작성하는 일이 아니라, **하나의 서비스가 동작하는 전체 과정을 이해하는 일**이었다.
