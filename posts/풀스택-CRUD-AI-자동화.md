# 풀스택으로 게시판을 만들며, 반복되는 CRUD를 AI 자동화로 줄여본 경험

풀스택 공부를 하면서 게시글 작성, 수정, 삭제, 조회 같은 CRUD 기능을 여러 번 다시 만들어야 했다.

기능 자체는 어렵지 않았다.

라우트를 만들고, 컨트롤러를 작성하고, 데이터베이스 쿼리를 연결하고, 프론트엔드에서 API를 호출하는 흐름은 매번 비슷했다.

문제는 **비슷한 코드를 반복해서 작성하는 데 생각보다 많은 시간이 든다는 것**이었다.

이번에는 이 반복 구간을 AI로 자동화해보면서, 어디까지 자동화할 수 있고 어디서부터는 직접 판단해야 하는지를 정리해봤다.

---

# 처음에는 무엇을 자동화해야 할지도 몰랐다

처음에는 막연히 "AI에게 CRUD를 통째로 맡기면 빠르지 않을까"라고 생각했다.

그래서

> 게시글 CRUD 기능 만들어줘.

라고 요청했다.

결과는 그럴듯했지만 프로젝트에 그대로 쓰기는 어려웠다.

- 에러 응답 형식이 기존에 정해둔 구조와 달랐고
- 인증 미들웨어를 거치는 방식이 빠져 있었고
- 타입 정의가 프론트엔드와 백엔드에서 따로 놀았다

한 번에 맡기기보다, 반복되는 부분과 판단이 필요한 부분을 먼저 나눠야 한다는 걸 알게 됐다.

그래서 반복 작업을 다시 정리해봤다.

- 라우트 - 컨트롤러 - 서비스 - 레포지토리로 이어지는 뼈대 코드
- 요청/응답 타입 정의
- 테스트용 시드 데이터
- 기본적인 API 테스트 코드

이 네 가지는 매번 손으로 작성하던 부분이었고, 동시에 실수가 나더라도 크게 위험하지 않은 영역이었다.

---

# 뼈대 코드는 자동화하되, 규칙을 먼저 정했다

라우트와 컨트롤러를 자동으로 생성하기 전에, 프로젝트에서 지키고 있던 규칙을 먼저 정리해서 함께 전달했다.

```md
- 응답은 항상 { success, data } 또는 { success, error } 형태로 반환한다
- 에러는 { code, message } 구조를 따른다
- 인증이 필요한 라우트에는 authMiddleware를 적용한다
- 컨트롤러에서는 검증만 하고, 실제 로직은 서비스 계층에서 처리한다
```

이 기준을 먼저 주고 나서야 요청한 코드가 프로젝트 구조에 맞게 나오기 시작했다.

```ts
// posts.controller.ts
export const createPost = async (req: Request, res: Response) => {
  const { title, content } = req.body;

  if (!title || !content) {
    return res.status(400).json({
      success: false,
      error: { code: "INVALID_INPUT", message: "제목과 내용을 입력해 주세요." },
    });
  }

  const post = await postService.createPost({
    userId: req.user.id,
    title,
    content,
  });

  return res.status(201).json({ success: true, data: post });
};
```

이렇게 만들어진 코드는 그대로 쓰기보다, 기존 코드 스타일과 비교하면서 다듬는 용도로 사용했다.

**뼈대를 자동으로 채우고, 규칙에 맞는지는 직접 확인하는 방식**이 가장 잘 맞았다.

---

# 시드 데이터와 테스트 코드가 가장 크게 도움이 됐다

CRUD 기능을 확인할 때마다 매번 테스트용 데이터를 직접 입력하는 게 번거로웠다.

이 부분은 자동화 효과가 가장 컸다.

```ts
// seed.ts
const users = Array.from({ length: 5 }).map((_, i) => ({
  email: `user${i}@test.com`,
  nickname: `테스트유저${i}`,
}));

const posts = Array.from({ length: 20 }).map((_, i) => ({
  title: `테스트 게시글 ${i}`,
  content: "AI로 생성한 시드 데이터입니다.",
  authorId: (i % 5) + 1,
}));
```

시드 스크립트를 만들어두고 나서는

```
npm run seed
```

한 줄로 회원과 게시글 데이터를 다시 채울 수 있었다.

기능을 수정할 때마다 데이터베이스를 초기화하고 값을 다시 입력하던 시간이 확 줄었다.

테스트 코드도 비슷했다.

```ts
describe("POST /api/posts", () => {
  it("제목이 없으면 400을 반환한다", async () => {
    const res = await request(app)
      .post("/api/posts")
      .set("Authorization", `Bearer ${token}`)
      .send({ content: "내용만 있음" });

    expect(res.status).toBe(400);
    expect(res.body.error.code).toBe("INVALID_INPUT");
  });
});
```

기본적인 성공/실패 케이스를 AI가 먼저 초안으로 만들어주면, 여기에 실제 서비스에서 자주 발생하는 예외 상황을 추가하는 식으로 작업했다.

**"테스트 코드를 0에서 시작하지 않아도 된다"는 것만으로도 부담이 크게 줄었다.**

---

# 자동화가 대신해주지 못한 부분

반복 작업을 줄이면서도, 몇 가지는 끝까지 직접 판단해야 했다.

- 어떤 경우를 "정상"으로 보고, 어떤 경우를 "예외"로 볼 것인가
- 삭제된 게시글을 완전히 지울지, 상태만 바꿔서 남겨둘지
- 권한이 없는 사용자가 수정 API를 호출했을 때 어떤 상태 코드로 응답할지
- 같은 요청이 짧은 시간에 여러 번 들어왔을 때 어떻게 처리할지

이런 부분은 AI에게 물어봐도

> 프로젝트 정책에 따라 다릅니다.

같은 답이 돌아오는 경우가 많았다.

당연한 결과였다.

이런 판단은 코드가 아니라 **서비스가 어떻게 동작해야 하는지에 대한 기준**이었고, 그 기준은 결국 내가 정해야 하는 부분이었다.

자동화는 이 판단을 대신해주는 것이 아니라, 판단을 내린 뒤에 반복되는 구현을 빠르게 채워주는 역할에 가까웠다.

---

# 자동화 스크립트 자체도 관리 대상이었다

시드 스크립트와 테스트 코드를 자동으로 만들고 나서 끝이라고 생각했는데, 시간이 지나니 이것도 유지보수가 필요했다.

- 스키마가 바뀌면 시드 데이터도 함께 수정해야 했고
- API 응답 구조가 바뀌면 테스트 코드도 같이 고쳐야 했다

그래서 자동화 스크립트를 만들 때도 다음을 함께 고려하게 됐다.

- 어디까지 자동으로 생성하고, 어디부터는 수동으로 관리할지
- 스키마 변경 시 어떤 파일들을 함께 확인해야 하는지
- 자동 생성된 코드와 직접 수정한 코드를 어떻게 구분할지

자동화는 한 번 만들고 끝나는 작업이 아니라, **프로젝트와 함께 계속 맞춰가야 하는 대상**이라는 걸 알게 됐다.

---

# 풀스택 공부를 하며 자동화를 보는 관점이 바뀌었다

처음에는 AI 자동화를 "코드를 안 써도 되게 해주는 도구"로 생각했다.

지금은 조금 다르게 본다.

- 반복되고, 실수해도 위험하지 않은 부분은 자동화로 넘기고
- 서비스의 정책과 기준이 필요한 부분은 직접 판단하고
- 자동화된 결과물도 꾸준히 검토하고 관리해야 한다

풀스택 개발에서 프론트엔드, 백엔드, 데이터베이스의 책임을 나눠서 이해해야 했던 것처럼, AI 자동화도 **"어디까지 맡길지"를 먼저 나누는 게 먼저였다.**

무작정 다 맡기면 프로젝트에 맞지 않는 코드가 나왔고, 무작정 다 손으로 하면 반복 작업에 시간을 너무 많이 썼다.

---

# 마무리

풀스택 공부를 하면서 CRUD, 시드 데이터, 테스트 코드처럼 반복되는 영역에 AI 자동화를 적용해봤다.

가장 크게 느낀 것은, 자동화가 개발을 대신해주는 게 아니라 **반복되는 부분을 줄여서, 판단이 필요한 부분에 더 집중할 수 있게 해준다는 것**이었다.

라우트 뼈대나 시드 데이터처럼 규칙이 분명한 영역은 자동화로 넘기고, 정책과 기준이 필요한 영역은 직접 고민하는 식으로 나누고 나서야 자동화가 실제로 도움이 됐다.

앞으로도 새로운 기능을 만들 때마다

> 이 작업은 반복인가, 판단인가

를 먼저 구분하고, 반복인 부분부터 자동화 대상으로 삼아볼 생각이다.
