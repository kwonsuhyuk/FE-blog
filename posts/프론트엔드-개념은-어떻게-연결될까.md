프론트엔드를 공부하면서 렌더링, 상태, 캐시 같은 단어를 따로 외운 적이 많았다. 그런데 실제로 기능을 만들 때는 개념 하나만 알고 있다고 문제가 풀리지 않았다.

검색 결과가 이전 값으로 돌아가는 문제에는 비동기 처리와 상태가 같이 얽혀 있었다. 저장한 데이터가 화면에 안 보이는 문제에는 서버 상태와 캐시가 같이 들어 있었다.

따로 알고 있던 개념이 실제 코드에서는 어떻게 연결되는지 다시 정리해봤다.

## 1. 렌더링은 화면을 그리는 과정이다

렌더링은 데이터를 사용자가 볼 수 있는 UI로 만드는 과정이다.

React 컴포넌트에서는 props와 state를 읽어 JSX를 반환한다. 상태가 바뀌면 React는 컴포넌트를 다시 실행하고 이전 결과와 비교해 필요한 DOM만 반영한다.

```tsx
interface IUserProfileProps {
  name: string;
  role: string;
}

export function UserProfile({ name, role }: IUserProfileProps) {
  return (
    <section>
      <h2>{name}</h2>
      <p>{role}</p>
    </section>
  );
}
```

여기서 컴포넌트 함수가 다시 실행되는 것과 브라우저 DOM 전체가 다시 만들어지는 것은 다르다.

```text
상태 변경
→ 컴포넌트 다시 실행
→ 이전 결과와 비교
→ 달라진 DOM만 반영
```

그래서 리렌더링 자체를 무조건 없애려고 하면 안 된다. 먼저 어떤 상태가 바뀌었고, 그 상태를 어느 범위에서 읽고 있는지 봐야 한다.

## 여기서 중요한 포인트

- 렌더링은 현재 상태를 UI로 표현하는 과정이다
- 컴포넌트 재실행과 DOM 전체 교체는 같은 말이 아니다
- 성능 문제는 렌더링 횟수보다 비용과 범위를 같이 봐야 한다

---

## 2. 서버 렌더링과 하이드레이션은 이어지는 과정이다

Next.js에서는 서버가 먼저 HTML을 만들 수 있다. 브라우저는 이 HTML을 빠르게 보여주고, 이후 JavaScript가 연결되면서 버튼과 입력창이 동작하기 시작한다.

이 연결 과정을 하이드레이션이라고 한다.

```text
서버 : HTML 생성
브라우저 : HTML 표시
JavaScript 로드
React : 이벤트와 상태 연결
```

서버가 만든 결과와 브라우저가 처음 계산한 결과가 다르면 하이드레이션 불일치가 생길 수 있다.

```tsx
// 서버와 브라우저에서 값이 달라질 수 있다
export function CurrentTime() {
  return <span>{new Date().toLocaleTimeString()}</span>;
}
```

시간, `window`, `localStorage`처럼 서버가 알 수 없는 값은 클라이언트에서 읽어야 한다. 반대로 서버가 이미 알고 있는 데이터까지 클라이언트에서 다시 기다릴 필요는 없다.

| 값 | 서버에서 알 수 있는가 | 처리 위치 |
| --- | --- | --- |
| DB에서 읽은 게시글 | 가능 | 서버에서 먼저 렌더링 |
| 브라우저 너비 | 불가능 | 클라이언트에서 확인 |
| `localStorage`의 테마 | 불가능 | 마운트 후 확인 |
| URL의 검색 조건 | 가능 | 서버 또는 클라이언트 목적에 맞게 선택 |

→ 서버가 아는 값과 브라우저만 아는 값을 구분하면 렌더링 위치를 정하기 쉬워진다.

## 3. 상태는 누가 소유하는지부터 구분한다

상태라고 해서 모두 같은 방식으로 관리할 필요는 없다.

```text
지역 상태   : 모달 열림, 입력 중인 값
전역 상태   : 여러 화면이 함께 쓰는 사용자 설정
서버 상태   : API에서 받아온 게시글, 사용자 정보
URL 상태    : 검색어, 필터, 페이지 번호
```

예를 들어 상품 검색어를 무조건 전역 상태에 넣으면 새로고침이나 링크 공유가 어렵다. 검색어를 URL에 두면 현재 화면을 그대로 공유할 수 있고 뒤로 가기도 자연스럽다.

서버에서 받은 목록을 `useState`에 복사해 관리하면 원본과 복사본 중 무엇이 최신인지 애매해질 수 있다.

```tsx
// X : 서버 데이터를 다시 복사해서 두 개의 원본을 만든다
const { data } = useProductsQuery();
const [products, setProducts] = useState(data ?? []);

// O : 화면에서 필요한 값은 서버 상태로부터 계산한다
const { data: products = [] } = useProductsQuery();
const visibleProducts = products.filter((product) => product.isVisible);
```

> 상태를 어디에 둘지는 누가 읽는지와 누가 최신 값을 책임지는지로 결정한다.

## 여기서 중요한 포인트

- 가장 가까운 곳에서만 쓰는 값은 지역 상태가 먼저다
- 서버에서 온 데이터는 서버 상태 도구가 최신성을 책임지게 한다
- 공유와 복원이 필요한 조건은 URL 상태인지 확인한다

## 4. 불변성은 변경을 알아차리게 하는 규칙이다

React는 배열이나 객체 내부를 하나씩 검사하지 않는다. 이전 참조와 새 참조가 같은지 비교해 변경 여부를 판단하는 경우가 많다.

```tsx
// X : 기존 배열을 직접 변경
products.push(newProduct);
setProducts(products);

// O : 새로운 배열을 만들어 변경을 표현
setProducts((previous) => [...previous, newProduct]);
```

첫 번째 코드는 배열 내용은 달라졌지만 참조가 그대로다. React가 변경을 제대로 알아차리기 어렵고, 이전 상태도 이미 바뀌어 디버깅하기 힘들어진다.

객체도 마찬가지다.

```tsx
setUser((previous) => ({
  ...previous,
  name: nextName,
}));
```

불변성은 단순히 스프레드 문법을 쓰는 규칙이 아니다. 이전 값은 보존하고, 변경된 값은 새 참조로 표현한다는 약속이다.

## 5. 비동기 요청은 시작한 순서대로 끝나지 않는다

검색 기능을 만들면서 가장 헷갈렸던 부분이다. 먼저 보낸 요청이 항상 먼저 도착할 것처럼 코드를 작성하면 네트워크가 느린 환경에서 이전 결과가 최신 결과를 덮어쓸 수 있다.

```text
"react" 요청 시작
"react query" 요청 시작
"react query" 응답 도착
"react" 응답 도착 → 이전 결과로 덮어씀
```

디바운싱은 요청 횟수를 줄이지만 이미 시작한 요청의 순서를 보장하지 않는다.

```text
디바운싱       : 얼마나 자주 요청할 것인가
요청 취소      : 필요 없어진 작업을 멈출 것인가
최신성 검사    : 어떤 응답을 화면에 반영할 것인가
```

```tsx
const controllerRef = useRef<AbortController | null>(null);

const searchProducts = async (keyword: string) => {
  controllerRef.current?.abort();

  const controller = new AbortController();
  controllerRef.current = controller;

  const response = await fetch(
    `/api/products?keyword=${encodeURIComponent(keyword)}`,
    { signal: controller.signal }
  );

  return response.json();
};
```

데이터뿐 아니라 로딩과 에러 상태도 오래된 요청이 덮어쓸 수 있다. 요청 단위로 상태를 생각해야 하는 이유다.

## 6. 캐시는 복사본이고 무효화는 최신성을 맞추는 일이다

캐시는 같은 데이터를 매번 다시 계산하거나 요청하지 않기 위해 저장해둔 결과다. 빠르게 보여줄 수 있다는 장점이 있지만 원본이 바뀌면 복사본도 갱신해야 한다.

```text
DB의 게시글       : 수정된 제목
화면이 보는 캐시  : 이전 제목
```

저장 API가 성공했다는 사실만으로 모든 캐시가 자동으로 바뀌지는 않는다.

| 작업 | 의미 |
| --- | --- |
| 갱신 | 서버에서 최신 데이터를 다시 가져온다 |
| 무효화 | 기존 데이터를 오래된 값으로 표시한다 |
| 낙관적 업데이트 | 서버 응답 전에 화면을 먼저 바꾼다 |
| 롤백 | 요청 실패 시 이전 상태로 되돌린다 |

낙관적 업데이트는 빠르게 느껴지지만 실패 처리까지 포함해야 한다.

```tsx
const previousProducts = queryClient.getQueryData<IProduct[]>(["products"]);

queryClient.setQueryData<IProduct[]>(["products"], (previous = []) =>
  previous.map((product) =>
    product.id === updatedProduct.id ? updatedProduct : product
  )
);

// 요청이 실패하면 previousProducts로 되돌린다
```

→ 캐시를 사용한다면 언제 오래된 값이 되고, 누가 다시 최신으로 만들지도 같이 정해야 한다.

## 7. 인증과 인가는 질문이 다르다

로그인 기능을 만들 때 인증과 인가를 같은 의미로 사용하기 쉽다.

```text
인증(Authentication)  : 이 사용자가 누구인가
인가(Authorization)   : 이 사용자가 이 작업을 해도 되는가
```

로그인한 사용자라고 해서 다른 사용자의 게시글을 수정할 수 있는 것은 아니다.

```ts
export async function updatePost(postId: string, userId: string) {
  const post = await getPost(postId);

  if (post.authorId !== userId) {
    throw new Error("수정 권한이 없다");
  }

  // 권한 확인 후 수정
}
```

화면에서 수정 버튼을 숨기는 것은 사용자 경험을 위한 처리다. 실제 권한 검사는 서버에서도 해야 한다. 브라우저의 코드는 사용자가 바꿀 수 있기 때문이다.

## 여기서 중요한 포인트

- 로그인 여부와 작업 권한은 별도로 확인한다
- 클라이언트의 버튼 숨김은 보안 경계가 아니다
- 서버는 요청마다 해당 자원에 대한 권한을 검증해야 한다

## 8. 접근성과 테스트는 UI 구조를 확인하는 기준이 된다

버튼을 `div`로 만들고 클릭 이벤트만 붙여도 마우스로는 동작한다. 하지만 키보드와 스크린 리더에서는 버튼으로 인식되지 않는다.

```tsx
// X : 모양만 버튼
<div onClick={openDialog}>추가</div>

// O : 역할이 드러나는 요소
<button type="button" onClick={openDialog}>
  추가
</button>
```

역할이 분명한 UI는 테스트하기도 쉽다.

```ts
await page.getByRole("button", { name: "추가" }).click();
await expect(page.getByRole("dialog")).toBeVisible();
```

CSS 선택자로만 찾을 수 있는 UI라면 사용자가 그 요소의 역할을 이해할 수 있는지도 확인해볼 필요가 있다.

접근성과 테스트는 기능을 다 만든 뒤 추가하는 별도 작업처럼 보였다. 지금은 컴포넌트의 역할과 사용자 흐름이 제대로 표현됐는지 확인하는 기준에 더 가깝다고 생각한다.

---

## 개념을 연결해서 보면

상품 수정 기능 하나에도 여러 개념이 동시에 들어간다.

```text
사용자가 수정 버튼을 누른다
→ 이벤트가 클라이언트 상태를 바꾼다
→ 서버는 인증과 권한을 확인한다
→ DB의 원본 데이터가 바뀐다
→ 캐시를 갱신하거나 무효화한다
→ React가 최신 상태로 다시 렌더링한다
→ 테스트가 사용자 흐름을 검증한다
```

| 문제가 보이는 위치 | 먼저 확인할 개념 |
| --- | --- |
| 화면이 예상보다 많이 다시 그려짐 | 상태 위치, 참조, 렌더링 범위 |
| 새로고침할 때 화면이 달라짐 | 서버 렌더링, 하이드레이션 |
| 검색 결과가 이전 값으로 돌아감 | 비동기 순서, 요청 취소, 최신성 |
| 저장했는데 화면은 그대로임 | 서버 상태, 캐시, 무효화 |
| 버튼은 눌리는데 테스트가 찾지 못함 | 시맨틱 HTML, 접근성 |
| 로그인했는데 수정하면 안 되는 데이터가 수정됨 | 인증, 인가 |

## 자주 하는 실수

### 1. 모든 상태를 전역으로 만든다

여러 곳에서 쓸 가능성이 있다는 이유만으로 전역 상태부터 만들면 데이터의 소유자가 불분명해진다. 실제로 공유되는 시점에 올려도 늦지 않다.

### 2. 서버 데이터를 지역 상태에 그대로 복사한다

원본이 두 개가 되면 동기화 코드가 필요해진다. 화면용 값은 가능한 한 서버 상태로부터 계산하는 편이 단순하다.

### 3. 요청 성공과 화면 갱신을 같은 일로 본다

DB가 바뀌는 것과 캐시가 바뀌는 것은 별개의 과정이다. 저장 이후 어떤 데이터를 갱신할지까지 기능에 포함해야 한다.

### 4. 화면에서 버튼만 숨기면 권한 처리가 끝났다고 생각한다

클라이언트 UI는 보안 기준이 될 수 없다. 실제 자원 접근 권한은 서버가 확인해야 한다.

---

## 정리

- 렌더링은 상태를 UI로 표현하는 과정이다
- 서버가 아는 값과 브라우저만 아는 값을 구분해야 한다
- 상태는 소유자와 최신성의 책임에 따라 위치를 정한다
- 불변성은 변경을 새 참조로 표현하는 규칙이다
- 비동기 요청은 완료 순서가 달라질 수 있다
- 캐시는 복사본이므로 갱신 전략이 필요하다
- 인증과 인가는 서로 다른 질문이다
- 접근성과 테스트는 UI 역할을 확인하는 기준이 된다

## 마무리 하며

예전에는 개념을 하나씩 설명할 수 있으면 이해했다고 생각했다. 실제 기능에서는 개념 사이의 경계를 알아야 문제를 찾을 수 있었다.

앞으로 새로운 기술을 공부할 때도 사용법만 정리하기보다, 기존 개념 중 무엇과 연결되는지 같이 기록해보려고 한다.
