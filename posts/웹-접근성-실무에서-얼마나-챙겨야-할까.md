QA 피드백에 "스크린 리더로 읽었을 때 버튼 이름이 안 나온다"는 항목이 올라온 적이 있다. 처음 든 생각은 "이미지에 alt 텍스트 몇 개 빠뜨렸나" 정도였다. 코드를 열어보니 문제는 훨씬 넓게 퍼져 있었다.

## 접근성은 스크린 리더 사용자만의 문제가 아니다

여기서부터 통념이 하나 깨졌다.

접근성이라고 하면 보통 시각장애인용 스크린 리더를 떠올린다. 맞기는 한데 전부는 아니다.

- 마우스 없이 키보드로만 이동하는 사용자
- 손목 부상으로 클릭보다 탭(Tab) 이동이 편한 사용자
- 밝은 야외에서 저대비 화면을 보는 사용자
- 이어폰 없이 자동재생 영상을 마주친 모든 사용자

즉 접근성은 "특정 소수를 위한 배려 기능"이 아니라 **입력 방식과 환경이 다른 사용자를 놓치지 않는 것**에 가깝다. 그리고 이건 의외로 시맨틱하지 않은 HTML 한 줄에서부터 무너진다.

---

## 1. 시맨틱 HTML이 절반이다

가장 흔하게 보이는 패턴이 이거였다.

```tsx
// X
<div onClick={handleClick}>삭제</div>

// O
<button onClick={handleClick}>삭제</button>
```

`div`에 `onClick`만 걸어도 화면에서는 똑같이 클릭이 된다. 문제는 스크린 리더나 키보드 사용자에게는 이게 그냥 텍스트일 뿐이라는 점이다. 포커스가 가지 않고, Tab으로도 닿지 않고, 스크린 리더는 "버튼"이라고 읽어주지도 않는다.

`button`, `a`, `input`, `label` 같은 시맨틱 태그는 이런 것들을 브라우저가 기본으로 처리해준다.

- 키보드 포커스 가능 여부
- 스크린 리더가 역할(role)을 읽어주는지
- Enter/Space로 동작하는지

이걸 `div` + `onClick`으로 다시 만들려면 `tabIndex`, `role`, `onKeyDown`을 전부 손으로 붙여야 한다. 굳이 그럴 이유가 없다.

## **여기서 중요한 포인트**

- `div`, `span`은 스타일을 위한 태그다. 동작이 필요하면 시맨틱 태그로 바꾸는 게 먼저다
- "클릭되니까 됐다"는 마우스 사용자 기준의 판단이다

---

## 2. 포커스는 보이고, 갇히지 않아야 한다

두 번째로 자주 놓치는 부분은 포커스 관리다.

```css
/* X */
button:focus {
  outline: none;
}
```

디자인 시안에 없는 파란 테두리가 거슬려서 지우는 경우를 꽤 봤다. 근데 이 `outline`이 키보드 사용자에게는 "지금 여기 있다"를 알려주는 유일한 신호다. 지우는 순간 키보드로는 어디에 포커스가 있는지 전혀 알 수 없어진다.

```css
/* O */
button:focus-visible {
  outline: 2px solid var(--color-primary);
  outline-offset: 2px;
}
```

`:focus-visible`을 쓰면 마우스 클릭 시에는 테두리가 안 보이고, 키보드로 이동했을 때만 보인다. 디자인과 접근성을 동시에 만족시키는 절충안이다.

모달에서는 반대 방향의 문제도 생긴다.

```tsx
function Modal({ onClose }: { onClose: () => void }) {
  const dialogRef = useRef<HTMLDivElement>(null);

  useEffect(() => {
    dialogRef.current?.focus();
  }, []);

  return (
    <div
      ref={dialogRef}
      role="dialog"
      aria-modal="true"
      tabIndex={-1}
      onKeyDown={(e) => {
        if (e.key === "Escape") onClose();
      }}
    >
      {/* 모달 내용 */}
    </div>
  );
}
```

모달이 열렸는데 포커스가 배경 페이지에 그대로 남아있으면, 키보드 사용자는 모달이 뜬 줄도 모르고 뒷배경을 계속 탐색하게 된다. 열릴 때 포커스를 모달로 옮기고, `Esc`로 닫히게 하는 것까지가 최소한이다.

## 3. ARIA는 마지막에 쓴다

`aria-*` 속성을 보면 만능 해결책처럼 느껴질 때가 있다. 실제로는 순서가 반대다.

> **No ARIA is better than Bad ARIA.**

시맨틱 태그로 해결되는 걸 굳이 `div role="button"`으로 만들고 ARIA를 붙이면, 브라우저 기본 동작(키보드 지원 등)까지 전부 직접 구현해야 한다. 그래서 아이콘 버튼처럼 시각적 텍스트가 없는 경우에만 최소한으로 쓰는 게 맞다.

```tsx
// 아이콘만 있고 텍스트가 없는 버튼
<button aria-label="검색">
  <SearchIcon />
</button>
```

```tsx
// 실시간으로 바뀌는 영역, 예: 폼 에러 메시지
<p role="alert" aria-live="polite">
  {errorMessage}
</p>
```

`aria-label`은 시각적으로 보이는 텍스트가 없을 때, `aria-live`는 사용자가 포커스를 옮기지 않아도 스크린 리더가 변경 사항을 읽어줘야 할 때 쓴다. 우선순위는 항상 시맨틱 HTML → 그래도 부족할 때 ARIA다.

## 4. 자동 검증으로 최소 기준부터 잡는다

접근성을 사람이 매번 눈으로 확인하는 건 지속 가능하지 않다. 그래서 기계가 잡을 수 있는 것과 사람이 확인해야 하는 것을 나눠서 생각하는 게 편했다.

| 기계가 잡는 것              | 사람이 확인해야 하는 것            |
| ---------------------------- | ----------------------------------- |
| alt 속성 누락                | alt 텍스트가 실제로 맥락에 맞는지  |
| 명도 대비 수치 미달          | 대비는 통과했는데 실제로 읽기 불편한지 |
| 폼 요소에 label 누락         | 에러 메시지가 원인을 제대로 설명하는지 |
| 키보드로 닿지 않는 인터랙티브 요소 | 탐색 순서가 실제로 자연스러운지    |

```ts
// e2e/a11y.spec.ts
import { test, expect } from "@playwright/test";
import AxeBuilder from "@axe-core/playwright";

test("메인 페이지 a11y 위반 없음", async ({ page }) => {
  await page.goto("/");

  const { violations } = await new AxeBuilder({ page })
    .withTags(["wcag2a", "wcag2aa"])
    .analyze();

  expect(violations.map((v) => v.id)).toEqual([]);
});
```

이런 테스트를 CI에 하나 걸어두면 최소한 "완전히 놓친" 케이스는 배포 전에 걸린다. 다만 이게 접근성을 다 챙겼다는 뜻은 아니다. 도구는 구조적 결함만 잡을 뿐, "이 문구가 실제로 이해가 되는가"는 여전히 사람이 봐야 한다.

## **여기서 중요한 포인트**

- 자동 검증은 바닥을 까는 용도다. 통과했다고 접근성이 좋다는 뜻은 아니다
- 그래도 바닥을 안 깔아두면 회귀가 조용히 쌓인다

---

## 자주 하는 실수

### 1) `div` + `onClick`으로 인터랙션을 만든다

동작하는 것처럼 보이지만 키보드/스크린 리더 사용자에게는 존재하지 않는 버튼이다.

### 2) alt에 파일명이나 의미 없는 텍스트를 넣는다

```tsx
// X
<img src="/banner.png" alt="이미지" />

// O
<img src="/banner.png" alt="9월 신규 기능 소개 배너" />
```

alt가 없는 것보다야 낫지만, 내용을 설명하지 못하면 있어도 없는 것과 비슷하다.

### 3) 포커스 아웃라인을 디자인 이유로 지운다

키보드 사용자의 유일한 위치 신호를 없애는 것과 같다.

### 4) 색으로만 정보를 구분한다

```tsx
// X: 빨간 텍스트로만 에러 표시
<p className="text-red-500">필수 항목입니다</p>

// O: 색 + 아이콘/텍스트로 이중 전달
<p className="text-red-500 flex items-center gap-1">
  <AlertIcon /> 필수 항목입니다
</p>
```

색맹이거나 저채도 화면을 쓰는 사용자는 색 하나만으로는 정보를 못 받는다.

---

## 정리

- 접근성은 시각장애인만을 위한 게 아니라 입력 방식과 환경이 다른 모든 사용자를 위한 것이다
- 인터랙션이 필요하면 `div`보다 시맨틱 태그를 먼저 쓴다
- 포커스는 보여야 하고, 모달 같은 곳에서는 갇히지 않아야 한다
- ARIA는 시맨틱 HTML로 안 될 때 최소한으로 쓴다
- 자동 검증(axe-core 등)으로 바닥을 깔고, 그 위는 사람이 확인한다
- 색만으로 정보를 전달하지 않는다

---

## 마무리 하며

접근성을 완벽하게 챙기는 건 현실적으로 어렵다고 생각한다. 그런데 이번에 코드를 다시 보면서 느낀 건, 완벽함이 목표가 아니라 **최소한을 놓치지 않는 것**이 먼저라는 점이었다.

`div` 대신 `button`을 쓰는 것, 포커스 아웃라인을 지우지 않는 것. 거창한 작업이 아닌데도 안 되어 있는 곳이 생각보다 많았다. QA 피드백 하나 덕분에 다시 들여다보게 된 부분이라, 잊지 않으려고 정리해봤다.
